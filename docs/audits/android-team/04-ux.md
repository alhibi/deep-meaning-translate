# A4 — UI/UX and Android device experience audit

- **Repository:** `deep-meaning-translate` @ `c897209` (branch `main`; the only file written by this audit is this report).
- **Auditor:** `ux` (independent subagent), 2026-11-16, Europe/Berlin.
- **Operating contract:** `AGENTS.md` read first; evidence order used = executable gates → source → docs. Docs were treated as claims; contradictions are recorded, not resolved silently.
- **Method:** static source inspection of `src/styles.css`, `src/routes/*`, `src/components/translator/*`, `src/components/stats/*`, `src/lib/i18n.ts`, `theme.ts`, `platform.ts`, the persistence boot path, the bundled native build in `android-web/`, all Android resource XML/Kotlin/build files, and the design/Android docs. **One executable gate was run by this auditor:** `node scripts/check-contrast.mjs` → exit 0, 51/51 pairs.
- **Not done by this auditor (by mission constraint):** no APK build, no install, no emulator interaction, no browser/server run. The lead owns the central APK build. Anything that can only be seen on a running app is classified **NOT_VERIFIED** and listed in the matrix; it is never reported as observed.

---

## 1. Summary verdict

The product's identity survives the Android packaging: the three palettes (dark clay / light paper / vivid electric) are intact, the palette is still expressed as one set of semantic tokens, the translator is still one fixed screen, fonts are bundled with the APK (`android-web/assets/*.woff2`, 19 font files), the contrast gate passes (51/51, re-run), focus-trap dialogs are in place, and reduced-motion rules exist. There is **no P0** (no crash or data-loss path found in this scope).

The Android _device experience_ is nevertheless not release-clean. Six issues matter most:

1. **The saved appearance is not restored on Android.** The pre-paint boot scripts read `localStorage`, which the Android app never writes (settings live in DataStore), and the one function that applies the DataStore values (`applyStoredAppearance()`) is called **only when the bridge fails**. Result: the user's theme choice silently reverts to the system palette on every cold start, and the first-run intro replays whenever no draft is restored. Docs claim the opposite (`docs/android/architecture.md:49-57`).
2. **Android Back exits the app while a language / model / voice sheet is open.** The back handler knows only the overlays whose state lives in `src/routes/index.tsx`; the source/target pickers, `BrainPicker` and `VoiceSheet` are local state, so Back falls through to `App.exitApp()` instead of closing the sheet — the exact opposite of the documented order.
3. **The "keyboard open" canvas stage can never engage under `adjustResize`.** `index.tsx:392` compares `visualViewport.height` with the _current_ `window.innerHeight`; on Android the WebView (or the Capacitor IME padding) shrinks both together, so the 150 px delta never appears. The documented strip-collapse and auto-scroll to the newest result do not run.
4. **The composer's clear (X) button sits on the wrong side whenever UI direction differs from typed-text direction** — i.e. in the default German-UI + Arabic-source use case. It overlaps the first line and the reserved 56 px padding is on the opposite side.
5. **System-bar icons are synced exactly once at boot and only for the status bar.** Toggling to Paper leaves white status-bar icons on a light surface; the navigation bar is never synced at all.
6. **Splash/launcher identity assets are not release quality.** The splash icon is a 48 dp foreground bitmap with a baked cream square, upscaled and circularly masked on API 31+; the adaptive-icon foreground is 48 dp instead of 108 dp; an unused default Android-robot vector is still shipped. The splash background is hard-coded clay, so Paper/Vivid users get a dark splash followed by a light app.

The remaining findings (P2/P3) cover touch-target sizes below the project's own 44 px contract, Arabic letter-spacing from arbitrary Tailwind tracking, the composer's removed focus indicator, a low-contrast focused placeholder, an error that becomes visually silent when a previous result is on screen, a non-theme-aware splash, the Saved sheet's `vh` (vs `dvh`) height, missing bottom safe-area padding on secondary pages, `dvh`/`lh` having no fallbacks for old WebViews, silent 5000-character truncation, a hard-coded English `aria-label` on the native boot cover, and the missing Android share-target parity for "send text to today".

**Release recommendation:** fix A4-01..A4-06 before calling the APK a stable daily-use release; the P3 list is worth one cleanup pass after that. Everything marked NOT_VERIFIED below still needs the device checklist in `docs/android/device-compatibility.md` on the available emulator.

## 3. Detail on the leading findings

### A4-01 — the native boot never applies the saved appearance (P1)

`src/lib/platform.ts` hydrates the DataStore snapshot and returns on success:

```ts
// platform.ts:79-100
try {
  const snapshot = await withBootTimeout(nativePort.hydrate(), BOOT_TIMEOUT_MS);
  hydratePersist(...); hydrateHistory(...); hydrateSaved(...); hydrateMemory(...);
  lastError = null;
} catch (error) {
  lastError = ...;
  try { applyStoredAppearance(); } catch { /* ... */ }
}
ready = true;
```

`applyStoredAppearance()` (lines 56-69) is the only code that turns the stored `lingua.theme.v1`, `lingua.ui-locale` and `lingua.intro.seen.v1` into the document theme class, `dir`/`lang`, and the intro gate. It is **only** reachable from the failure branch. The success path leaves the theme to the pre-paint scripts, and those scripts read `localStorage`:

- `src/lib/theme.ts:30` — `THEME_BOOT` uses `localStorage.getItem("lingua.theme.v1")`;
- `src/lib/i18n.ts:612` — `LOCALE_BOOT` uses `localStorage.getItem("lingua.ui-locale")`;
- `src/lib/intro.ts:24` — `INTRO_BOOT` uses `localStorage.getItem("lingua.intro.seen.v1")`.

But on Android these keys are **never** written to localStorage: `settings.ts:11` states "There is no localStorage mirror", `writeDeviceValue` branches to DataStore from `nativeMode = true` (`settings.ts:73-86`), and `hydratePlatform` calls `setNativeSettingsMode(true)` at line 78 before any React code runs. The pre-paint scripts run before that, so their reads are always empty and the fallbacks are used (system colour scheme; system language; intro open).

Consequences, in order of user visibility:

1. **Theme choice lost** on every cold start (this is the P1). The theme toggle writes the choice correctly (`theme.ts:83`), so the setting survives in DataStore but is never read back into the document.
2. **UI locale/direction** comes from the system language (WebView `navigator.languages`) rather than from the saved in-app choice. `initLocale()` (`i18n.ts:626-630`, called from `index.tsx:238`) corrects it after mount; the splash normally masks the transient frame, but the documented "direction applied before paint" (`docs/design/system.md:112`, `docs/android/architecture.md:51`) is false for the installed app.
3. **Intro replay** — see A4-02.

This contradicts the documented boot sequence (`docs/android/architecture.md:49-57` lists `applyStoredAppearance()` as a step after the bridge boot) and the comment in `platform.ts:18-20` ("applies the saved palette and direction ... before React render"). The code is evidence; either the document is wrong or the code is missing a call.

**Fix (smallest coherent change):** invoke `applyStoredAppearance()` at the end of the successful `try` block (before `ready = true`); React has not rendered yet because `hydratePlatform()` is awaited behind the boot cover/splash. Add the platform success-path regression test. The boot-cover frame still uses the pre-paint scripts, so the follow-up "mirror the three boot keys into localStorage" is what makes the _very first_ frame correct too; it can be a separate commit but should be scheduled before release.

### A4-02 — the first-run intro replays (P2)

`introPending()` answers "did the pre-paint CSS gate open?", not "has this person seen the intro?". On Android the gate always opens because `INTRO_BOOT` reads localStorage. The route then decides:

```ts
// index.tsx:261
const wantsIntro = !pick && !shared && !session?.text && introPending();
```

So any launch with no restored draft (empty composer, first install, after "clear") shows the welcome overlay again, even though `shouldShowIntro()` would consult the DataStore flag (`intro.ts:7-11`). The bridge-failure branch already demonstrates the intended correction: `platform.ts:67` releases the gate when `INTRO_KEY === "1"`. Same root cause as A4-01; using `shouldShowIntro()` for the decision and applying the stored appearance on success fixes it. Device-visible, not a data-risk — hence P2 rather than P1.

### A4-03 — Back exits the app with a picker open (P2)

The handler is state-based:

```ts
// index.tsx:661-699 (abridged)
if (savedOpen) return setSavedOpen(false);
if (dialectOpen) return setDialectOpen(false);
if (localeOpen) return setLocaleOpen(false);
if (lexOpen) return setLexOpen(false);
if (shadowMapOpen) return setShadowMapOpen(false);
if (shadowFocus) return setShadowFocus(null);
if (introOpen) return finishIntro();
...
void (async () => { const { App } = await import("@capacitor/app"); await App.exitApp(); })();
```

The source/target picker (`LanguageBar.tsx:43-44`), the model picker (`BrainPicker.tsx:19`) and the voice sheet (`ResultPanel.tsx:122`) are not in that list. Because `platform.ts:168-170` registers a Capacitor `backButton` listener, the dependency never falls back to `WebView.goBack()` (`AppPlugin.java:46-58`), so the pushed history entries those sheets create are never used by the system back path, and the handler reaches `App.exitApp()`.

This is not cosmetic: changing language is frequent, and pressing Back to dismiss the picker closes the app. The documented order (`docs/android/architecture.md:84-94`) is overlay → keyboard → history → exit. The minimal fix in section 2 keeps the state-based closers and adds a generic "a modal is open → history.back()" step before the exit branch (all these overlays push history and pop it in cleanup: `LanguageSheet.tsx:180-202`, `stats/Sheet.tsx:85-111`). A cleaner long-term fix is a single overlay stack shared by route and children.

### A4-04 — keyboard detection vs Android `adjustResize` (P2)

```ts
// index.tsx:386-396
const height = Math.round(vv.height);
...
const open = height < window.innerHeight - 150;
```

The comparison assumes the layout viewport keeps its full height while only the visual viewport shrinks — the classic "keyboard overlays the page" model. This app is configured for the opposite model: the manifest uses `adjustResize` (`AndroidManifest.xml:32`, `styles.xml:13`), the Capacitor keyboard plugin is set to `resize: "native"` (`capacitor.config.ts:37-40`), and Capacitor 8's `SystemBars` additionally pads the decor view by the IME inset on API 30+ (`patches/@capacitor+android+8.6.2.patch`; the patch explicitly reasons about "the window is already resized for the IME"). The viewport meta also opts into `interactive-widget=resizes-content` (`__root.tsx:26`). In all of these cases `window.innerHeight` shrinks together with `visualViewport.height`, so the 150 px delta never materialises (or flickers for one event). The `data-keyboard="open"` CSS block (`styles.css:1503-1509`) and the "pin the newest result" effect (`index.tsx:412-417`) are then dead on the target platform. The canvas still fits the screen (`--vvh`/`dvh` shrink), so the user can scroll — but the documented composer/result strip behaviour is not delivered and the newest answer can sit below the fold while typing.

The existing e2e geometry test (`tests/e2e/field_layout.py`) only asserts stillness at 390×844 with no keyboard; it cannot catch this. The proposed regression test (viewport shrink after a baseline snapshot) models `adjustResize` correctly and would fail on today's code.

### A4-05 — the composer's clear button overlaps text in mixed directions (P2)

```tsx
// index.tsx:795-797, 805, 813, 853
<section dir={uiRtl ? "rtl" : "ltr"} className="source-stage input-shell relative px-5 pb-2 pt-5">
  <textarea dir={rtlInput ? "rtl" : "ltr"} ... className="autogrow ... pe-14 ..." />
  ...
  <button ... className="press absolute end-3 top-4 grid size-10 ..." >
```

The section's direction is the **UI** locale, so `end-3` is a physical side chosen by UI language. The textarea's direction is the **typed text**, so `pe-14` reserves space on the typed text's inline-end. When the two differ (German UI + Arabic text in one direction; Arabic UI + German text in the other), the X is drawn on the side where the text begins and the reserved padding is on the opposite side. With `top-4` and no background, the X overlaps the first line's leading glyphs.

The same two-direction mix exists in the spoken overlay above the textarea (`index.tsx:819-843`, `dir={rtlInput}` inside the section).

### A4-06 — bar icons are stale after a theme change (P2)

```ts
// platform.ts:108-121
const light = document.documentElement.dataset["theme"] === "light";
await StatusBar.setStyle({ style: light ? Style.Light : Style.Dark });
```

This is the only call. `useTheme.toggle()` (`theme.ts:77-131`) changes the palette, persists the choice, and never touches native chrome. The legacy `@capacitor/status-bar` plugin sets only the status bar (`StatusBar.java:42-51`); the navigation bar is set only by Capacitor 8's built-in `SystemBars` plugin, which the app never calls (the JS API is available from `@capacitor/core`: `SystemBars.setStyle({ bar, style })`). In Paper theme on a system configured dark, both bars render light icons over a light surface.

### A4-07 — a failure next to an old result is visually silent (P2)

`useTranslator.ts:290-292` deliberately keeps the previous good result; `ResultPanel.tsx` then takes the `result` branch and never renders the translated `err_*` copy. The only trace is:

```tsx
// ResultPanel.tsx:481-491
{error ? (
  <button ... className="press-soft animate-fade ms-auto ... text-[12px] ...">
    <RotateCw className="size-3" /> {error === "offline" ? t("offline") : t("retry")}
  </button>
) : null}
```

The translated error copy exists (`i18n.ts` `err_*`) but is only shown when `result === null`. For a meaning-first product, showing a stale translation with no "this did not translate" message is an integrity hazard: the user can copy the previous sentence's translation believing it answers the new text. Proposed: keep the old result but add the translated error line (warning dot + copy + retry) and a stale marker until the retry settles.

### A4-08 / A4-09 — launch identity

A4-08 is an asset-contract problem, measurable from the repo: the adaptive-icon foreground is a 48 dp bitmap (192 px at xxxhdpi = 48 dp, not the 108 dp / 432 px the adaptive format expects) with a baked cream background, the adaptive background is pure white (`values/ic_launcher_background.xml:4`) while the legacy icons are cream, and the splash theme reuses that same bitmap as the launch icon (`styles.xml:25`). On Android 12+ the splash icon is circularly masked and scaled up, so the first thing a user sees is a blurred cream square/disc; the automated check the repo already uses for APK contents (`aapt2 dump badging`) does not catch it. The in-app intro uses the vector-clean `/icon-monochrome-320.webp` (`Intro.tsx:88-99`), which shows what the correct mark looks like.

A4-09 is the colour half: the native splash/window background is dark clay for every user (`styles.xml:7-8,24`, `capacitor.config.ts:33`), and there is no `values-night` resource, so a Paper/Vivid user always crosses a palette boundary at launch. This is visible in source and cannot be fixed by the web layer, because the splash is native.

## 6. Notes, limitations, and documentation drift

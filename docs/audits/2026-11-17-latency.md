# Translation Latency Audit — 2026-11-17

Status: **Executed (historical for the routing policy)**. This record answers one report:
translation and model replies became slow and take extra time. The automatic failover/cooldown it
describes was later **superseded by strict model selection** (2026-11-18, see the
[strict-model audit](2026-11-18-strict-model-immediate.md)); the measurements and the settle-clock
finding remain valid evidence. Every number below was measured in this environment on 2026-11-17 between
23:34 and 23:56 Europe/Berlin; classifications follow [testing](../quality/testing.md)
(VERIFIED / OBSERVED / SUSPECTED / NOT_VERIFIED). Nothing here is inferred from a README.

## 0. Scope and method

- Baseline: published `origin/main` at `3c78ab7` ("Present the translation models as Velo and
  Sona"), served at `https://fluently.today` through Cloudflare (edge FRA), plus a local
  production preview built from the same tree.
- Measured at three boundaries so provider time, server time and screen time are not confused:
  1. the DeepSeek API directly with the exact production prompts and task profiles
     (`tests/eval/probes.ts` request shapes);
  2. the deployed `/api/translate-stream` (headers, first chunk, complete body);
  3. the browser: in-page `fetch` wrapper timestamps every stream request relative to the last
     keystroke, and the DOM is polled for first text, `aria-busy` and action availability.
- Both writers were probed: Velo (`brain: "deepseek"`) and Sona (`brain: "luna"`).
- No request content, key or translation is printed in this document. Live probes used synthetic
  sentences only.

## 1. Findings

### F1 — Sona was slow because it failed every request and the retry ran before the fallback (VERIFIED)

Four consecutive deployed Sona requests, same text and profile:

| probe | response headers | first byte | total | `x-translation-writer` |
| ----- | ---------------- | ---------- | ----- | ----------------------- |
| live  | 3,600 ms         | 4,181 ms   | 4,363 ms | `deepseek` |
| live  | 3,425 ms         | 3,557 ms   | 3,670 ms | `deepseek` |
| live  | 3,453 ms         | 3,807 ms   | 3,938 ms | `deepseek` |
| full  | 3,356 ms         | 3,741 ms   | 4,041 ms | `deepseek` |

Every Sona request was actually written by Velo. The same route answered in 745–826 ms of headers
when Velo was requested. The arithmetic identifies the mechanism: the OpenCode attempt is a
transient failure (rate/provider), `providers/retry.server.ts` retried it after the provider's
`Retry-After` clamped to 2.5 s, and only then did `streamRoute.server.ts` fall back, so the
person waited for a dead provider **plus** the healthy one. The fallback was invisible in the UI:
the result simply arrived four seconds late.

Root cause: the pre-stream retry was unconditional, although another configured writer could
answer immediately, and the route kept no memory of the failure, so every following sentence paid
the same 2.5 s again.

### F2 — the settled reading's pause clock was anchored to the live answer (VERIFIED)

A 44-character Arabic sentence without a final punctuation mark, typed at a normal speed into the
deployed app, traced in the page (times relative to the last keystroke):

| event | before |
| ----- | ------ |
| final live request starts | +510 ms |
| final live headers | +1,348 ms |
| final live first text | +1,873 ms |
| final live complete | +1,976 ms |
| **full request starts** | **+3,181 ms** |
| full headers | +4,015 ms |
| full complete | +4,719 ms |
| settled (actions enabled) | ≈4.7 s |

The full request left 1.2 s after the live stream *completed*, not 1.2 s after the person stopped
typing. The pause effect in `useTranslator.ts` declared `provisional, phase, result` as its
trigger, so it could only start counting once the live answer arrived. A word without punctuation
behaved the same way: full request at +3,167 ms, settled ≈4.2 s. The provider's own full answer
takes 0.7–1.2 s, so most of that time was queueing, not model time.

Root cause: a pause is a property of the text, but the timer was anchored to the transport.

### F3 — the server hot path loaded four modules in series before contacting the provider (OBSERVED)

`handleTranslateStream` awaited `import("./providers/opencode.server")`, then `import("./types")`,
then `import("./providers/deepseek.server")`, then `import("./engine.server")` before any provider
byte could leave. Locally the old bundle's server overhead measured within provider noise (live
headers 296–414 ms against 282–416 ms for the direct call; full headers 303–323 ms against
282–309 ms), so this is not the reported slowdown on a warm instance. It is a cold-instance cost,
and the warm-up path did not preload `engine.server`/`types` at all. Fixed because it is free to
fix, but it is not claimed as the user-visible cause (no cold-start measurement was possible from
here: NOT_VERIFIED).

### What was not the cause (VERIFIED)

- **No app-imposed throttling.** During the traced sentence the client metrics were
  `requests: 5, cacheHits: 0, retries: 0, timeouts: 0, errors: {}`; the per-purpose admission
  buckets (live 120 burst / 4 per second, settled 90 / 2 per second) are far above a human typist,
  and no 429 was observed.
- **The model was not clamped.** Live capability probe against the deployed provider:
  `GET /models` returned `deepseek-flash` and `deepseek-v4-pro`; `max_tokens: 393,216` was accepted
  and `393,217` returned the documented 400; `thinking: {"type":"disabled"}` produced no reasoning
  tokens (the default produced them, confirming the explicit toggle works); JSON mode returned
  valid JSON; the SSE stream ended with `[DONE]` and carried usage; a client abort stopped the
  stream after 273 ms. A 4,900-character German→Arabic full answer used 12,740 ceiling / 1,625
  completion tokens, finished `stop`, parsed, and passed the deterministic verifier — 12.7 % of
  the ceiling, so the cap is not truncating real answers.
- **Provider time itself is healthy.** Direct calls with the production payloads: live first byte
  387–991 ms, complete 532–1,177 ms; full first byte 429–806 ms, complete 739–1,192 ms (3 rounds
  each). The deployed route adds ≈0.35–0.45 s of edge/network time over the direct call (Velo
  headers 745–826 ms), recorded as an environment limit, not an app regression.
- **Background work did not hold the foreground.** Foreground translation never enters
  `enqueueEnrichment`; the dictionary/shadow/review queue only starts after the settled answer is
  committed (140 ms gap, one job at a time, 8 s hang timeout).

## 2. Fixes

| # | Fix | Files |
| - | --- | ----- |
| 1 | **Immediate failover with the retry kept where it matters.** `fetchWithRetry` now takes `maxAttempts`. The writer that starts a request makes one attempt (`maxAttempts: 1`) when a usable fallback waits behind it, so a refusing provider is replaced without waiting out the clamped `Retry-After` (up to 2.5 s). The **last usable writer keeps the bounded retry**, so a transient failure of the only healthy provider is still healed (an independent review caught the first version of this fix stripping that resilience; the tests now pin both sides). A single-writer deployment always keeps the retry. | `providers/retry.server.ts`, `providers/deepseek.server.ts`, `providers/opencode.server.ts`, `streamRoute.server.ts` |
| 2 | **Provider cooldown.** A writer that just failed is skipped for a bounded window (rate 30 s, network 10 s, provider 15 s, auth/quota 5 min) while the other writer can answer; a success clears it. A fallback failure is recorded too, so the next sentence does not route into it blindly. The response gains a content-free `X-Translation-Fallback` header (also exposed to the Android origin gate), and the server log gains `requested`, `fallback`, `upstreamMs`. | `providers/health.server.ts` (new), `streamRoute.server.ts`, `native/gate.server.ts` |
| 3 | **The settle clock starts at the last text change.** A still-provisional draft that has been unchanged for the same 1,200 ms now starts its full reading then, whether or not the live stream has finished. The live stream for that draft is superseded by the full request (the full commit remains the only way provisional text becomes final). No extra requests: a 44-character no-punctuation sentence still spends two live streams and one full request. | `useTranslator.ts` |
| 4 | **Hot path loaded in parallel**, and the warm-up preloads `engine.server`/`types` as well as both providers. | `streamRoute.server.ts` |

## 3. Evidence after the fixes

### Local production preview (same provider, same prompts)

| measure | before | after |
| ------- | ------ | ----- |
| full request start (no-punctuation sentence) | +3,181 ms (deployed trace) | **+1,165 ms** |
| settled (actions enabled) | ≈4.7 s (deployed trace) | **1,955–2,654 ms** (built production bundle, provider variance) |
| provider requests for the sentence | 2 live + 1 full | 2 live + 1 full |
| route headers for a warm Velo request | 296–414 ms | 296–414 ms (unchanged, within noise) |

The same measurement on a single word: settled 4,177 ms → **2,079 ms**. A sentence that ends with
punctuation already took the direct full path and is unchanged (settled 1,763–2,169 ms locally,
depending on a legitimate source/target re-route).

The final built bundle was also probed directly for both writers: Velo live headers 316–485 ms /
first byte 555–748 ms; a Sona request with no local OpenCode key failed over in **284 ms** (first
byte 528 ms) and the next one skipped the unusable writer entirely (299 ms) — against
3,356–3,600 ms before the fix. The provider requests per sentence did not grow: two live streams
and one full request for a 44-character no-punctuation sentence, one full request for a completed
sentence.

## 4. Limits and remaining debt

- **The OpenCode/Luna account is the remaining external failure**: four of four probes failed on
  2026-11-17. The app now fails over immediately and cools the writer down, but it cannot make an
  unavailable provider answer. Recorded as TD54 (provider availability, not app code).
- **The provider health memory is per server instance** (two entries, bounded), like the admission
  buckets; a deployment-wide breaker belongs at the hosting edge (TD5).
- **Edge latency**: the deployed route adds ≈0.35–0.45 s over a direct provider call from this
  network. That is Cloudflare egress/edge behavior, not application work; it is measured, not
  silently accepted as zero.
- **No production cold-start measurement** was possible: the deployed isolate lifecycle is opaque
  from here. The parallel-import change is a defensive improvement, not a claimed fix (NOT_VERIFIED).
- **Human/device perception**: all timings above are headless Chromium on a development machine
  and the Cloudflare edge; a phone on a mobile network adds its own latency (NOT_VERIFIED on a
  physical device in this audit).

## 5. Post-deploy verification (production)

Published and verified on 2026-11-18 00:33–00:41 Europe/Berlin. The served assets changed from
`index-BzrVFFIL.js`/`routes-C3Rd-qAD.js` (pre-fix) to `index-BPtCvKg6.js`/`routes-Bll3cgn_.js`
(the build produced by this commit), so the numbers below are the fixed code on
`https://fluently.today`, not a local preview.

| deployed probe | before | after |
| -------------- | ------ | ----- |
| Velo live response headers | 826 ms | 783–866 ms |
| Velo full response headers | 745 ms | 1,048 ms (the provider was slower during this window; see below) |
| Sona live response headers | 3,356–3,600 ms | **840–916 ms** |
| Sona live total | 3,670–4,363 ms | **1,549–1,686 ms** |
| UI full request leaves after the last keystroke (44-char, no punctuation) | +3,181 ms | **+1,409 ms** |
| UI settled (same browser trace) | ≈4.7 s | ≈3.3–3.5 s |

- **Sona is still refused by its provider**: all three deployed Sona probes returned
  `x-translation-writer: deepseek` with `x-translation-fallback: rate`. The app now pays only one
  fast attempt on the refusing writer (~0.1 s) before the healthy one answers; it no longer waits
  out a 2.5 s `Retry-After`. The provider-side rate limiting itself is external and remains TD54.
- **The cooldown is per server instance and did not visibly persist** across these three requests
  (all showed `rate`, not `cooldown`): the deployment routes requests to fresh isolates, so the
  bounded process-local record only helps when an isolate is reused. That is why the fix does not
  depend on it: the direct saving is the removed retry wait.
- **Provider variance is larger than the app overhead in this window.** A tiny-word trace saw the
  full request leave at +1,790 ms and take 1,788 ms to response headers, settling at ≈4.0 s, while a
  second Velo full call took 1,048 ms of headers. The application-side start is fixed at
  1.2–1.8 s; the rest is the provider plus the measured ≈0.35–0.45 s Cloudflare edge path. The
  local production bundle (same code, no edge) measured 1,955–2,654 ms settle for the same three
  cases, so the remaining production gap is network/provider time, not queueing in the app.
- **Request count unchanged**: two live streams and one full request for a 44-character
  no-punctuation sentence; one full request for a completed sentence. No extra paid calls were
  introduced by the settle-clock fix.
- **No app throttling or errors** appeared in the traces (`requests` incremented, `retries: 0`,
  `errors: {}`; no 429 from the app's admission buckets).

Status: the two measured root causes are **fixed and production-verified**; the OpenCode/Luna
provider refusal is **confirmed and external** (TD54).
